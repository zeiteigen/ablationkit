Manage your workspace

Keep execution, tracking delivery, and research records healthy without confusing their states.

Set agent permissions and compute limits

Open Project settings → Agents . Review the action policy for local jobs, remote jobs, and deployments, and the agent sessions that reported into the project. Preview changes before saving a new policy revision. Set the project's agent compute limit in weighted hours.

Where agents' jobs run is yours, never the agent's. The two job settings together are the project's pool: this workstation if local jobs are allowed, then the remote targets you tick. AblationKit queues each agent job and starts it on the first target of the pool with a free slot. Until one frees, the Jobs page shows the job as queued , with what it waits for, and Cancel takes it out of the queue. Jobs that need no GPU, such as tests and checks, run on this workstation at once without a slot. Agent permissions shows the pool and its busy slots. An agent cannot name a target, and an empty pool refuses its jobs.

On Compute , inspect agent usage; open Compute weights to set per-target weights and slots. The weights determine how execution time counts toward the agent limit; they are not a currency price. The slots are how many jobs needing a GPU run on a target at once: 1 by default, so agents' GPU jobs on this workstation take turns, and 2 for a Colab target. Your own jobs never wait, but they take a slot while they run. A session identifies the agent and attributes its work. Its Git access and sandbox come from the harness, unless you run it in an agent container , where AblationKit decides what it can reach and pauses it when the compute limit refuses its job.

Read the enforcement status

Resource limits can be advisory when the process supervisor uses its direct-mode fallback. A job's page reports enforcement, and so does Compute → Targets → This workstation; the status bar's health item says it on hover. Do not interpret a displayed limit as a guarantee that every process is constrained.

Use remote compute

The CLI sets up SSH, Slurm, Runpod, and Colab targets (Colab: see Run jobs on Google Colab ). Start with ablationkit target list and use ablationkit help for target-specific setup. Once configured, choose the remote target when you submit a job yourself. Agents' jobs go to targets you allow in the project's pool (see agent permissions ).

A remote attempt executes a staged bundle of a pinned commit and uploads results. Use Compute and job details to follow it. Offline reconciliation may be needed after a connection interruption; a remote drain delivers the leftover spool and does not rerun the experiment.

Run jobs on Google Colab

A Colab target runs each job on its own Colab runtime, unattended. AblationKit drives Google's Colab CLI ( colab ): it allocates the runtime, uploads the job's bundle, starts it, brings results back while it runs and after it ends, and stops the runtime. Once the project allows it, agents' jobs are placed on it like on any target of the pool, so nobody has to open a notebook.

  1. Install the CLI and sign it in once with the Google account that holds your Colab plan or compute units: 
    uv tool install google-colab-cli
colab sessions
    Open the link it prints, approve, and paste the code back. The token stays in your keyring; AblationKit never sees it.
  2. Add the target with the GPU to use ( T4 , L4 , G4 , A100 or H100 ; or --tpu v5e1 ), then check it: 
    ablationkit target add colab --kind colab --gpu L4
ablationkit target doctor colab
    The doctor reports the CLI, its sign-in, the account's compute units and the runtime it will ask for.
  3. To let agents use it, open Project settings → Agents , allow remote jobs and add colab to the allowed targets: it joins the project's pool, after this workstation. Set its weight on Compute so a Colab hour counts as you want against the agents' compute limit, and its slots to the number of runtimes your account may run at once (2 by default).

Compute → Targets shows the Google account's compute units: what is left, what its runtimes use per hour, and how many runtimes it holds (the whole account, including runtimes you started yourself). A job's remote panel shows its runtime's rate and the units it used so far, an estimate from how much the account's rate rose when the runtime was allocated.

Limits

The job does not need this workstation while it runs, but Colab can still reclaim a runtime (usage limits, a runtime's maximum lifetime); the attempt then ends with what was collected so far and is never rerun. A runtime whose results nobody collected is held for an hour after the job ( --keep-after-sec ), then left idle for Colab to reclaim. An accelerator the account cannot have, or a CLI that is not signed in, fails the submission before anything runs. Results come back through the runtime's file API, so keep artifacts small. To run notebooks yourself instead, add the target with --notebook .

Check tracking before repeating work

The status bar at the bottom of every page shows one health item, the coordinator and MLflow, which opens Settings → System; hover it for the rest. It adds an item only when something needs a look: a delivery backlog or failure, remote work, running jobs, live updates reconnecting, safe mode, or a modified build.

Symptom Next step
Job finished, results missing Inspect its console and delivery state. Check Settings → System for MLflow health and the delivery backlog.
Tracking delivery failed Use tracking diagnostics and retry the failed operation once the underlying problem is fixed.
Moved checkout Use project remap, then project doctor to check the registered path.
Signed out Run ablationkit ui on the workstation for a new one-time sign-in link.
Diagnostic commands 
ablationkit tracking doctor
ablationkit tracking status
ablationkit tracking outbox --failed
ablationkit project doctor --project PROJECT_ID

Back up and recover

Create a backup before changing storage or moving the coordinator. Settings → System shows backups and recovery controls. 

ablationkit backup create
ablationkit backup list
ablationkit backup verify BACKUP_ID

Replace BACKUP_ID with an ID from the list. Restore and coordinator moves require the coordinator to be stopped. Consult ablationkit help for restore paths and project remapping options. Do not treat vault export as a full backup.

Manage extensions and sessions

Project settings → Extensions contains build, enable, and rollback controls for project extensions and bundled backends. Read their capability and trust information before enabling them. If an extension prevents startup, restart with ablationkit coordinator restart --safe-mode to boot with extensions inactive.

In Settings → Agent sessions , inspect the harness, label, directory, last use, and attributed work. End session revokes its token. Machine-wide notification and authentication controls are under Settings → Preferences, and the coordinator's health under Settings → System (also at /system ).
