Your first project

Start with a small, known command. Once its results are visible, add more experiments or ask an agent to investigate a question.

  1. Start the coordinator and register your checkout

    With AblationKit installed, run these commands on the workstation. Replace the example path with your repository's absolute path. 

    ablationkit coordinator start
ablationkit project add /absolute/path/to/project
ablationkit ui

    The last command opens a one-time sign-in link. If you are running from the AblationKit source checkout without installing the CLI, prefix commands with bun run .

  2. Open the project

    Choose it in the sidebar. Open Project settings , choose its task profiles, and check the project doctor if setup is incomplete. Profiles control the visibility of backend pages. Data & Evals and Models wait under More until the project logs a model or runs an evaluation; a page under More is still available.

  3. Launch a short job

    Open Runs → Jobs → Launch job . Enter a command such as python train.py --lr 0.01 that exists in your checkout. Choose the project uv environment or system PATH, set the relative working directory, and supply suitable time, CPU, and memory limits.

    Open the resulting job to inspect its attempts and console. To record metrics, parameters, and artifacts, instrument your program with the job SDK or configure the launch dialog's metrics file and artifact globs. A successful process alone does not supply scientific results.

  4. Inspect the results

    Open Runs , select the recorded run, and inspect its metrics, parameters, tags, and artifacts. If delivery is pending, check Settings → System before rerunning the experiment. Continue with Run and compare .

Connect your coding agent

Agents that do the research get the agents' MCP server, ablationkit mcp . In an agent container (below) it is set up for them. Your own agent on this machine gets the executive's server instead ( ablationkit executive , further down), which is what scripts/setup.sh registers. To run a research agent on this machine without a container, add ablationkit mcp to its harness yourself (or run scripts/setup.sh --agent-mcp ). The server finds the project from the directory it starts in, or a parent.

Claude Code setup 
claude mcp add ablationkit -- ablationkit mcp
Codex MCP configuration 
[mcp_servers.ablationkit]
command = "ablationkit"
args = ["mcp"]

Each MCP process creates one agent session. You can inspect and end sessions in Settings → Agent sessions , and a project's own in Project settings → Agents .

The server offers nine tools. ablationkit_project , ablationkit_read and ablationkit_wait only read, so you can allow them without a prompt (in Claude Code, mcp__ablationkit__ablationkit_read in your allowed tools). ablationkit_wait is how agents wait for their jobs instead of sleeping in a shell: it returns when a job ends with its results in, starts, or reaches a training step, after at most an hour per call, and at once when you write a direction or change the agenda. ablationkit_job , ablationkit_run , ablationkit_task , ablationkit_note and ablationkit_work record the agent's work, and ablationkit_do does the rest (research records, deployments, LLM prompts and golden sets, extensions). The project policy and the compute limit apply to every call, whatever you allow.

A useful first request

“Track this investigation as an AblationKit task. Run a short baseline, explain what its metrics show, and write the findings as vault notes in a notebook. Keep the run within five minutes.”

For your agent on this machine, which oversees the research rather than doing it, the executive's server (registered by scripts/setup.sh ): claude mcp add ablationkit-executive -- ablationkit executive . It reads every project and runs the agents (starts, prompts, waits on, pauses and stops contained agents, and writes directions marked as its own), but cannot submit jobs, write notes or change policy.

Set agent permissions and compute limits before asking an agent to run substantial work.

Run your agent in a container

Optionally, AblationKit can run your harness for you in a rootless Podman container, so that what the agent itself does is bounded too. The container has no GPU, no Python environment of the project's (everything that runs the project's code, tests included, runs as a job, which the compute limit counts), no network except the hosts the project allows, and no view of AblationKit's own home. Its jobs run in job containers that get the GPU unless they ask for none; the agent installs packages with an environment build, itself a job, and the jobs read what it installed. Your agent still uses the same ablationkit_* tools.

  1. Prepare this machine once

    Install Podman and tmux (on Arch Linux, sudo pacman -S podman passt tmux ), then run ablationkit agent doctor and ablationkit agent image build . For GPU jobs, also generate a CDI spec: sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml .

  2. Start a session

    In the registered checkout, run ablationkit agent start (Claude Code), or add --harness codex or --harness shell . Arguments after -- go to the harness. Your terminal attaches to the container's. Claude Code starts signed in with your login from ~/.claude , kept in step while the session runs so neither side is signed out ( --no-login signs in inside instead). Codex signs in inside the first time; its home is kept per project. Detach with Ctrl-b d, and come back with ablationkit agent attach SESSION .

    Claude Code starts in bypass permissions mode, because the container is the boundary. To start it in another mode, pass the mode after -- , for example ablationkit agent start -- --permission-mode default . Remote Control is on: the session appears in claude.ai/code and the Claude app as the project and label, and you can follow it and type into it from there ( --no-remote-control starts it without). Claude Code's own management tools are off: it keeps no auto memory, publishes no Artifacts, schedules nothing and does not message your other sessions. What it learns goes in the vault.

  3. Watch and steer it

    Agents , in the main navigation, shows every running agent as a tile with its terminal, live and in colour. Open one for its own page, which has its full terminal, the facts of its container, what it reached and what it changed, and its account. The same sessions are listed in Settings → Agent sessions and Project settings → Agents . From any of these you can:

    • Terminal shows its screen, read-only.
    • Egress lists every connection it made and every one that was refused, with an Allow button for a refused host.
    • Pause freezes it, Resume thaws it, and Stop ends it.

    When the compute limit refuses one of its jobs, the session is paused until you resume it. Its Account shows what the container was given, where it connected, and what it changed.

  4. Decide what it may reach

    ablationkit agent allow HOST adds a host to the project's allowlist. Package indexes are not on it: the agent installs nothing itself. When an environment build is refused a host (a private index), ablationkit agent allow --environment HOST lets environment builds reach it. ablationkit agent config edit sets the rest:

    • paths agents must not see (held-out data, evaluation code) and paths they may only read;
    • whether job containers get the GPU and network;
    • protected evaluations, whose pinned command an agent can run against data it cannot read;
    • credentials the proxy adds, so that the secret never enters the container.

An agent of yours on this machine, outside a container, acts for you and may use the whole ablationkit command, including restarting the coordinator. It can start a contained agent with ablationkit agent start --detach -- "first prompt" , read its terminal with ablationkit agent screen SESSION and type into it with ablationkit agent send SESSION TEXT ; each input is recorded with its text.

Limits: the agent can still run CPU experiments in its shell within the container's limits. Hidden files inside the checkout stay in Git history, so keep protected data out of the repository. HTTPS connections are recorded by host only. The container sees your real checkout, so its record of changed files includes your own edits made meanwhile.
